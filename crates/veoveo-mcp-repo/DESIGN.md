# Repo MCP Design

Lore repositories for agents and people. It shows what people, and the agents working for them, did in the repositories a person can read: what changed, what it
looks like and what is running, and what the repositories hold. It only views. It is where Lore's API grows, as tools over the same reads.

It reads as the person who asked, through the Hub, so Lore's rules decide every read. It keeps only small pictures it was handed.

## Service Identity

```text
repository   veoveo-mcp-repo
slug         repo
URI scheme   repo
permission   repo.files.read
MCP          /repo/mcp
liveness     /livez
readiness    /readyz
port         8808
```

The server is named for what people look at, and Lore stays the name of the service that holds it: a file still opens on the Hub's `/view/lore/` page, and is still
read through the Hub's `/lore/` routes. This server has no tables and never reaches Lore's schema.

## Domain Contract

| Kind | Name | Permission | Answer |
|---|---|---|---|
| Tool | `activity` | `repo.files.read` | `Activity`: a page of pushes across the repositories the caller can read, newest first, or of one `repository` and `branch`, with who, when, what they said and what the factory is doing with each. For one repository, each branch with its latest push |
| Tool | `changes` | `repo.files.read` | `Changes`: what one revision changed, each file and link, compared with the revision before it or `against` |
| Tool | `file_diff` | `repo.files.read` | `FileDiff`: a text file's change between two revisions as a unified diff, or that it is binary or too large |
| Tool, for its App | `summaries` | `repo.files.read` | `Summaries`: how much each of up to 64 pushes changed, and up to three of its files with a picture |
| Tool, for its App | `link_pushes` | `repo.files.read` | `LinkPushes`: the pushes a link's move brought in from its repository, at most 20 |
| Tool | `list_files` | `repo.files.read` | `FileListing`: without a `repository`, the repositories the caller can read; with one, a folder of it on `branch`, `main` by default, folders first |
| Tool, for its App | `thumbnail` | `repo.files.read` | `FileThumbnail`: a picture of a file, in base64, or none |
| Tool, for its App | `browse` | `repo.files.read` | `Browse`: one page of the repositories, of a folder or of a `search`, with the pictures of what is on it that are ready |
| Tool, for its App | `covers` | `repo.files.read` | `Covers`: the files, at most four, that show each of up to 64 folders on its card |
| Tool, for its App | `thumbnails` | `repo.files.read` | `FileThumbnails`: what is ready of up to 64 files by one request, each a picture, nothing, or `pending` for `thumbnail` |
| App | `ui://repo/activity` | `repo.files.read` | The viewer, with the gallery as its Files view |

`thumbnail` asks the [Thumb server](https://github.com/VeoveoAI/veoveo-mcp-thumb/blob/main/crates/veoveo-mcp-thumb/DESIGN.md) as the same person, since a view reads only its own server. This server makes no pictures.

## What People Did

Agents do the editing, so this server is for seeing what they did. Everything is done by a person or on behalf of one: an agent pushes as the person it works for, and
that person is who a push names.

`ui://repo/activity` opens on **Activity**: one list of pushes across every repository the person can read, newest first by day, and one place to look at a push. Choosing a
repository and a branch narrows the same list. A push shows who pushed it, what they said, how much it changed, and small pictures of what it changed. Looking at it shows
the same at length, with a picture before and after for what has one, a diff for text, each link's move with the pushes it brought in, and whether the factory serves it. A
branch that forked also shows everything since it forked. **Branches** says, for each branch of a repository, its latest push and what the factory does with it, and
**Files** is the gallery below. Nothing here edits anything.

Everything comes from the Hub, read as the person, so Lore's rules decide:

| What | From |
|---|---|
| Repositories and branches | `GET /lore/{profile}/repositories` and `.../branches`, read again on each `activity`, so a page names only what the person may read now |
| A push | `.../history/{branch}`. A revision never changes, so what Lore says of one is held in memory by revision |
| What it changed | `.../changes/{revision}`, read each time, since what a person sees of a link depends on their grant on it. `summaries` keeps only counts and file names, by revision, after the person's repositories are read |
| A file before and after | `.../files/@{revision}/{path}`, which names one revision where a branch goes |
| What is running | `GET /factory/{profile}/instances`, as the person, read once per `activity` |
| Pictures | The Thumb server, handed `@{revision}` as the branch, which draws and keeps by content as it does for any file |

To list across branches, `activity` reads each branch's tip, takes the newest, and steps back along that branch, so it reads about one revision for each branch and for
each row shown, once, and only a branch's new tip after that. A branch that has no revision of its own yet says nothing, since the branch it forked from says it. A list goes
back at most 1000 pushes.

Lore's `ContentDiff` is not implemented, so `file_diff` reads both sides and makes the diff with `diffy`, which Lore's own client uses, for files up to 1 MiB and diffs up to
256 KiB. A file with a NUL in its first 8 KiB, or that is not UTF-8, is binary.

Lore's revision history holds no agents, so none is named. `Serving` and `Build failed` say what the factory is doing now, and it keeps no history of builds, so a failure
someone has since pushed past is not shown. The page reads again when the person asks, as a view does.

## The Gallery

The Files view opens on the repositories the person can read, then their folders and files, each folder's card showing pictures of
what it holds. The look and the behavior are [veoveo-hub-ui](https://github.com/VeoveoAI/veoveo-hub-ui)'s gallery. `assets/repositories.js`
says what is Lore's: how to list, what a location is, and the `/view/lore/{repository}/{branch}/{path}` page a file opens on.

This server, not the page, decides what a screen shows, so that a repository of any size costs a screen one request. One read of the Hub's
`/tree/` route names everything on a branch's tip, and a revision fixes everything under it, so what follows from that read is held in memory by
revision and needs no further read of Lore:

- **A folder's cover:** pictures of what it holds at any depth, a stage first, then one from each folder inside, leaving out text and code, which would
  show as small print.
- **An object:** a folder with exactly one stage in it, at any depth, or with a stage named for it beside other layers, is one object known by the folder's name, whatever the stage's file is called. It
  shows and opens that stage, and its closer look leads into its files.
- **A page and a search:** `browse` answers 60 items at a time, and `search` finds names at any depth, stopping at an object.

Each `browse` of a repository first reads its top as the person, so Lore decides whether they read it now and the answer names the tip; only a new tip reads
the whole tree again. A page of repositories reads none of them: it shows what was last known of each, which a person with a grant on it may see, and asks
`covers` for those not known yet.

Pictures come with the page. `thumbnails` and `thumbnail` keep each small picture the Thumb server answers, on disk, under what it shows: the file's
content address, and for a stage that is not a package the revision too, since it may name other files. `browse` answers from what is kept, up to 3 MiB a
page, and the page asks for the rest. While someone browses a repository, this server also draws what a gallery of its tip will ask for: each object's stage and every file outside an object that shows something, four at a time. It does so as that person, so Lore's and each server's rules still decide, and it lasts as long as their token. An open page asks again every 30 seconds while `browse` says `filling`, and any later request starts it again from what is not kept yet, so nobody runs anything for a repository to get its pictures. A stage whose tip is new shows its last picture until drawing ahead has asked about that tip, so an upload blanks nothing. A file with no picture is believed for an hour, since that may mean a draw failed. A page names only what its person's read listed, so what is kept reaches no one else, and any of it can be fetched again.

It shows `main` unless the page chooses a branch.

## Factory

`openshell/` holds the toolchain and the script that builds and starts the server. It asks for no GPU, no network rule and no provider.

## Persistence

No tables. The registration's `keys/` and the `pictures/` it was handed under `/sandbox/state`, all of which can be fetched again. An index is held in memory and read again after a restart.

## Qualification

| Layer | What it proves |
|---|---|
| Unit | Names, a listing's shape, what shows a folder, which folders are objects, a page and a search, kept pictures, the App's document, what the factory says of a revision, a file's diff, a summary |
| `tests/mcp.rs` | Discovery, permissions, a refused path, the App, the skill's manifest |
| Deployed | Grants deciding what a person sees, a link to a repository without a grant, and the viewer and gallery in browsers |
